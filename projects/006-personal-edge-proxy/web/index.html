库的能力
提供多入口、按目标选择出口的个人代理部署文档与配置范例；HY2 主用，VLESS / REALITY / Vision 备用，出口可选 Direct、WARP 或固定 SOCKS5。

个人出网、开发工具和 AI 服务访问、不同目标的出口管理，以及 UDP 受限时使用 TCP 备用接入。
对我们的价值
掌握入口与出口独立管理、协议分层和按层排障的方法；为将来的自建网关、配置校验和出口观测工具保留依据。实际收益需部署验证。

03 / PROTOCOL STACK

协议有哪些，它们各自负责什么？

同一条通道会组合代理协议、传输方式和安全层。

这套方案用到的代理协议主要是 Hysteria2、VLESS 和 SOCKS5。REALITY 提供接入安全与握手外观，Vision 优化流量处理；WARP 是出口服务，本例使用 MASQUE 隧道。它们处在不同层次。

代理协议 · 主入口

Hysteria2 / HY2

先建立基于 UDP 的 QUIC 加密连接，使用 HTTP/3 请求完成认证；然后发送“连接哪个地址和端口”的指令。TCP 数据走可靠的 QUIC 流，UDP 数据走 QUIC 数据报。

QUIC / TLS 握手 → 认证 → 目标指令 → 转发
QUIC 使用 TLS 1.3；UDP 数据报不会因为装进 QUIC 就自动变为可靠传输。[7]
代理协议 · 备用入口的一部分

VLESS

用轻量请求格式携带用户标识、目标地址、端口和转发指令。服务端验证用户后，再连接目标。这里的 VLESS 与 REALITY、Vision、TCP 配合使用。

用户标识 + 目标指令 + 待转发数据
研究版本配置为 decryption: none，未启用 VLESS 自身的额外加密；不能把这一配置推广到所有新版本。[2,12]
传输安全层 · 配合 VLESS

REALITY

修改 TLS 握手与验证方式，结合配置的密钥信息识别合法连接，并借用目标站点的 TLS 外观。认证通过后承载代理请求，未通过的连接可回落到配置的 target。

类似 TLS 的握手 → 验证 → 承载代理
这里的 target 是握手外观与回落目标，不是浏览器每次真正要访问的网站，也不是普通代理流量的固定中转站。[10]
流控与转发优化 · 配合 VLESS

XTLS Vision

在连接早期对内层握手做随机填充；对满足条件的 TLS 1.3 流量，可转为更直接地搬运已有密文，减少重复封装与处理开销。

识别流量阶段 → 填充 → 条件满足时优化
配置项为 flow: xtls-rprx-vision。它不是另一条独立入口，也不解密网站 HTTPS；效果需要实测。[12]
代理协议 · 连接上游出口

SOCKS5

双方先协商认证方式，再发送“请连接这个地址和端口”的请求，成功后转发数据。TCP 常用 CONNECT；UDP 有单独的 UDP ASSOCIATE 机制，需两端实际支持。

协商 / 认证 → 目标地址 → 代理转发
本例用它接本机 WARP 和远程固定出口。SOCKS5 自身不提供 TLS 式的传输加密；“固定”是上游 IP 属性。[5–6,14]
出口服务 + 隧道协议体系

WARP / MASQUE

Xray 将请求交给本机 WARP 的 SOCKS5 端口，warp-svc 再建立通往 Cloudflare 的隧道。本例记录使用 MASQUE：通过 HTTP 机制承载代理隧道，相关传输可基于 HTTP/3 / QUIC。

本地 SOCKS5 → warp-svc → Cloudflare
WARP 是服务，MASQUE 是隧道协议体系，二者不是同义词。本例没有部署 WireGuard 入口。[5,13,15]

把协议名放回实际链路

主入口：应用数据 → HY2 代理请求 → QUIC（含 TLS 1.3，基于 UDP）→ VPS

备用入口：应用数据 → VLESS + Vision → REALITY / TCP → VPS

WARP 出口：VPS 的 Xray → SOCKS5（本机回环）→ warp-svc / MASQUE → Cloudflare → 目标

可选应急入口：VLESS 数据可由 WebSocket 帧承载，经 Cloudflare 边缘与 Tunnel 到达 VPS；cloudflared 主动向 Cloudflare 建立连接。上游只提出这条思路，未提供对应示例。[1,16]

辅助概念：TCP / UDP 是基础传输；QUIC 在 UDP 上提供加密连接与多路流；TLS 保护传输内容；WebSocket 提供持续双向消息通道。TUN 是虚拟网卡接口，Xray / sing-box 是执行程序，Direct 是直接出网策略，它们都不应被当成独立的远程代理协议。

04 / UNDER THE HOOD

内部细节：三条边界，六个机制

把“谁接管”“怎么运输”“从哪出去”分开理解。

客户端边界应用请求如何进入代理
接入边界设备如何连接 VPS
出口边界VPS 如何连接目标
01

代理端口与 TUN

代理端口需要应用主动使用；TUN 是虚拟网卡，配合系统路由把流量交给客户端核心。客户端仍可按规则让部分目标直接访问，不经过 VPS。

02

应用协议与隧道协议

浏览器的 TCP 数据可以放进 HY2 的 QUIC 通道。QUIC 基于 UDP，并为流提供可靠传输。因此“HY2 用 UDP”不代表网页数据就没有可靠性保障。

03

认证与连接封装

客户端携带目标域名或 IP、端口和数据。HY2 用密码认证并验证 TLS 证书；REALITY 示例结合 VLESS 用户标识、公私钥及 shortId 等配置校验接入。

04

域名、DNS 与嗅探

域名可能由客户端直接提供，也可能从可见的 HTTP/TLS/QUIC 信息中识别。嗅探不等于解密 HTTPS；DNS 在哪解析取决于配置，不能仅凭 TUN 就保证无泄漏。

05

按顺序匹配路由

Xray 从上到下使用首个命中规则。此示例先阻断私网，再匹配固定 SOCKS5 与 WARP；未命中则走首个 Direct 出站。WARP 示例规则仅匹配 TCP。

06

建立连接与双向转发

常见 TCP 场景中，代理建立到目标的连接，持续转发两边的字节流。响应沿同一逻辑代理链返回，浏览器最终收到网页或 API 结果；VPS 无需运行浏览器。

依据：服务端示例 [2]、HY2 协议 [7]、Xray 路由与入站文档 [8–9]。这些是协议和配置层解释，未声称在本机部署验证。

05 / ENCRYPTION & VISIBILITY

代理保护接入，HTTPS 保护应用内容

HTTPS · 内层浏览器 ⇄ 目标网站

正常证书验证且没有中间人解密时，网站内容、密码和 API 数据由应用层 TLS 保护。

HY2 / REALITY · 外层本机代理 ⇄ VPS

保护这一段接入传输；VPS 终止外层代理通道后，继续转发内层数据。

每一方能知道什么？

你的设备
应用原始请求、代理设置及客户端接入凭据。
VPS / 上游出口
连接地址、可见的目标信息、流量大小和时间；正常 HTTPS 内容不会因此自动解密。明文应用流量没有这层保护。
目标网站
应用请求、账号/Cookie 等，以及最终出口的公网 IP。换出口 IP 并不消除账号身份。

“内外两层”用于区分保护范围，不表示所有字节始终重复做两次 TLS 加密；Vision 可对符合条件的内层 TLS 1.3 数据优化转发。[12]

SOCKS5 自身没有传输加密。 公网上的 VPS → SOCKS5 上游这一段，协议凭据和元数据需要另行考虑保护；目标使用 HTTPS 时，应用内容仍有自己的 TLS 保护。WARP 的本地 SOCKS5 段则在 VPS 回环地址上，之后由 WARP 建立上游通道。[5–6]

沉淀：网关工具的设计基础

和我们研究过的 Tailcat 有什么区别？

Tailcat：重点是让两台设备在复杂网络中建立按需连接。
Personal Edge Proxy：重点是让客户端经 VPS 访问互联网目标，并控制最终出口。两者可解决不同问题，不能仅因都使用加密通道就视为同一种工具。

07 / LIMITS & NEXT STEPS

理解边界，才能判断是否值得继续

它解决不了的事情

  • VPS 的线路质量、拥塞和丢包不会因为多加一层就自动改善。
  • WARP 不保证住宅 IP、固定 IP、账号安全或某个服务一定可用。
  • 多入口仍可共用同一台 VPS；VPS 故障时，不会自然变成多机容灾。
  • 示例没有给出完整自动切换、监控平台、用户管理或稳定性承诺。
  • 域名规则可能漏掉新域名或不同传输。示例 WARP 规则只含 TCP，不能推定所有 UDP/HTTP3 都走 WARP。

可以继续开发的方向

  1. 配置工具：生成客户端与服务端配置，并检查版本、密钥和规则。
  2. 出口仪表盘：持续检查每条出口的 IP、连通性和失败原因。
  3. 路由验证：维护域名和 DNS 策略，验证关键请求是否命中。
  4. 多 VPS 容灾：实测接入切换，并保持需要固定的出口策略。
  5. 运行维护：凭据轮换、证书到期提醒、日志保护和故障恢复。

本栏是我们的设想，尚未实现。

本次研究的证据边界：阅读并核对公开文档与配置；没有购买或部署 VPS，没有测得速度、稳定性或账号可用性数据。网页和图表是本仓库独立制作的理解材料。
