# Grok Bot Field Notes 研究记录

## 结论

`unicodef1wn/grokbot-field-notes` 的价值首先在于留下了一个具体产品案例：三名工程师用 Grok Bot Agent 辅助开发，从快闪活动构想转向浏览器自动对战游戏，并公开发布 **Thursday Arena**。产品真正遇到的问题包括方向反复、玩法规则漏洞、客户端可信状态、上线用户路径和自动修复引发的生产故障。原仓库把这些经验进一步整理为可讨论、可改写的工程资料。它本身是第三方文档与模板集，不包含可独立运行的 Grok Bot 产品、模型或通用 Agent 执行服务。

对于本研究仓库，优先借鉴“先弄清原团队交付的产品，再追问真实问题”的研究顺序，以及固定事实来源、用户路径验证和高影响改动的风险门槛。大量角色模板与复杂编排在工作量、权限和交接问题真实出现时再选择使用。

## 价值再评估：有用内容与个人增量应分别判断

对已有成熟工程经验的使用者，先复现、明确职责、实际验证、控制权限与成本等原则通常已被理解。该库主要把这些原则应用到 Agent 工作场景，新增方法有限。它的剩余价值在于具体事故的情境、模板整理以及遗漏检查，可节省查阅和整理时间。

资料是第三方直播整理，部分事件缺少完整代码、独立事故分析和长期结果。案例出现、提出修改、记录修复和证明长期有效是不同的证据层级。资料数量、角色数量及 PR 数量不能替代质量或商业效果证据。

因此，本项目的投入判断为：**归档参考，降低持续深入优先级；遇到实际问题时查对应案例或模板，再结合自己的环境验证。** 这是针对当前需求的研究判断，并不否认其对入门者的组织和教学价值。

该结论已整合进 [全量理解引导图](web/assets/understanding-guide.svg)，并提供 [PNG 版](web/assets/understanding-guide.png)。图中的八类模块、五类成果和使用建议属于本研究归纳；图由本仓库制作，不是原项目界面。

## 对话形成的综合理解与迁移路线

本研究将其定位为 **Agent 辅助产品开发与业务工作的工程案例、操作手册和模板资料库**。它的材料来源既有三天产品开发，也有穿插其中的九类岗位演示；作者将原始过程进一步整理为可阅读、可改写的资料。岗位演示中的部分公司、客户和数字是演示素材，不能当作 Thursday Arena 的实际经营数据。依据见固定版本的 [README](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/README.md) 和 [岗位流程说明](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/playbooks/README.md)。

### 适用方向与后期如何使用

可参考的方向包括：设计单个 Agent、组织多个角色、使用 Agent 编码、从原型推进到产品发布、设计客服营销等业务流程，以及管理例行任务成本。对当前研究项目集，优先完善一条完整交付路径：

1. 带着一个实际问题读对应材料，写清目标与完成信号。
2. 将方法改成自己的规则，填写真实来源、命令、目录和权限条件。
3. 由一个 Agent 跑通一个真实任务，记录缺失信息、返工和无法验证的结果。
4. 把重复有效的步骤封装为技能或工作流，包含检查与异常处理。
5. 用交付可信度、人工返工、执行频率和实际成本决定是否扩展角色或自动运行。

以上是本研究的迁移建议，不表示原库提供现成执行系统，也不表示本次已安装技能或建立多 Agent 团队。

### 具体问题、处理与经验

下表的事件与处理均来自三天笔记的二次整理。若笔记没有明确给出修复结果，就只写“登记”或“调查”。

| 问题 | 资料记载的处理 | 可迁移经验 |
| --- | --- | --- |
| 第 1 天快闪方向反复变化，客户、许可与运营范围未收束 | 继续调研、修改落地页；次日转向游戏 | 先验证产品问题和现实约束 |
| 第 2 天普通卡牌属性总和不符合 100 点规则；传说卡牌仍只合计 100 | 普通卡牌经提示修正并重载验证；传说卡牌问题被提出，未证实当天解决 | 将玩法规则写成可自动检查的不变量 |
| 第 2 天虚构 bot 和原型文案出现在公开页面 | 直播中发现并要求清理 | 将占位内容与真实产品内容分开验收 |
| 第 2 天免费刷新可反复刷高稀有度卡牌，浏览器中可改战斗属性 | 调整刷新机制，推动服务端掌握战斗状态 | 先明确哪些状态必须由可信系统决定 |
| 第 3 天排位持续匹配到 AI，ELO 却变化 | 先调查根因，不立即提交 PR；笔记后续报告问题不再出现 | 端到端检查承诺给用户的路径，而不只看页面表现 |
| 第 3 天代币花光可使玩家难以继续 | 直播中登记问题，笔记未提供修复证明 | 检查资源耗尽、空状态和恢复路径 |
| 第 3 天移动端布局问题集中出现，横幅遮住商店按钮 | 做响应式修改，用设备模拟复查 | 按真实设备分布检查窄屏和遮挡 |
| 第 3 天自主修复引入错误 SQL，短时影响生产与注册 | 团队恢复服务，笔记无独立事故报告 | 数据库与发布改动需要检查、权限边界和回滚准备 |

第 3 天笔记报告约 30,000 次页面浏览、超过 6,000 场公开对战、累计 433 个 PR，同时记载直播结束时实际收入为 0。这些是直播中报告的口径，未独立复算；既不能据此认定商业成功，也不能把 PR 数量当质量指标。

### 对当前研究仓库的投入判断

1. **产品先于工具：**每个研究项目先回答团队做出什么、给谁使用、核心流程是什么。工具和 Agent 体系服务于这个问题。
2. **证据分层：**把固定版本的第三方笔记、产品当前官网、本地实测与推断标清楚。特别防止把后来的官网状态倒填到直播当天。
3. **按用户路径验收：**公开链接、部署子路径、手机宽度和交互都要实际走一遍。这个案例的移动端遮挡与资源耗尽问题提示我们测试普通路径和边界状态。
4. **高风险任务设门槛：**Agent 先复现、再改动、附验证证据；数据库、权限和发布修改需要可执行检查与恢复手段。

## 一、库的能力

### 1. 项目级工作规则

[根目录 `AGENTS.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/AGENTS.md) 是一份可复制后修改的 Agent 工作规范。它要求 Agent 在修复前重现问题，说明完成证据，做小范围修改，实际运行应用，并在 PR 中写清证明和不确定事项。按变更类型，示例证据包括 UI 截图或录屏、性能前后数据、原问题复现与修复后通过的步骤。

它还列出何时转交人类决策，例如鉴权、支付、权限、用户数据、迁移、破坏性操作及生产部署。其“纠正后写一般原则”的做法有助于避免把单次事故写成长期、过度具体的提示词。

这些是 **写给 Agent 的指令和工作约定**。具体平台会不会读取该文件、如何处理优先级，以及能否阻止某种操作，仍取决于实际 Agent 环境、权限和仓库设置。

### 2. 验证工作的方法

[`agents/VERIFICATION.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/agents/VERIFICATION.md) 将验证定义为可重复执行的工作：把应用置于已知状态、运行命名流程、采集截图、检查不变量，失败时给出明确的错误信号。文件给出 `./verify seed`、`./verify run <flow>`、`./verify check` 等设计示例，还建议维护功能地图。

**边界：**这些命令是构建项目专属验证入口的范式。原资料库没有替任意网页、后端或研究项目写好实际的验证程序。对当前研究仓库而言，可检查的信号包括文件存在、图片和资源加载、相对路径、响应式布局、外链实际可访问、研究声明与来源一致。

### 3. 多 Agent 编排与职责模板

[`agents/ORCHESTRATION.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/agents/ORCHESTRATION.md) 描述如何定义窄职责、协调者、共享 playbook、例行任务和自治等级。它也指出 Agent 过多会带来额外的上下文、路由、费用和人的注意力成本。所谓调查、草稿、自动执行等等级是工作授权方式，仍需结合真实权限系统决定。

[`roster/README.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/roster/README.md) 的索引列出 69 种去重后的岗位模板。每个岗位说明负责和不负责的范围、事实来源、需审批事项、触发条件、输出及可粘贴的角色描述。它们是选择和改写的素材，不表示应创建 69 个 Agent。

[`playbooks/README.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/playbooks/README.md) 汇总 9 类岗位工作坊：工程、产品、创始人、售前工程、销售、SDR、客服、售后和营销。每类包含团队分工、工作流、提示词、例行任务及直播中提到的数字。它适合参考业务流程如何分解，实际数据接入与对外动作需重新设计。

### 4. 失败记录和成本观察

[`ANTIPATTERNS.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/ANTIPATTERNS.md) 归纳 40 个直播中的失败案例，以“发生什么、原因、形成的原则”组织。案例包括提示词约束未落实到检查、未测试上线当天的真实路径、将可信状态放在浏览器客户端、未明确交付边界、Agent 数量过多等。案例中对原因的解释属于资料作者整理；迁移时应判断自己项目是否具有相同问题。

[`reference/ECONOMICS.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/reference/ECONOMICS.md) 汇总直播中提到的单项成本、吞吐数字和费用来源。其文件自身提醒数字应视作量级，不是报价表。较稳妥的可迁移观察是：高频例行任务、群聊、重复的浏览器手动步骤以及角色膨胀会增加开销；实际收益要用本项目自己的运行记录验证。

## 二、技术本质：两个层次要分清

### 本资料库的实现层

本仓库主要由 Markdown 文档、PDF 指南、Cursor `.mdc` 规则、岗位文件和 PR 模板组成。其机制是 **外部化工作约束**：将角色、事实来源、执行范围、验证条件和纠正原则写成 Agent 与人可共享的资料。它本身不训练模型，不提供新的推理算法，也不通过文字规则自动产生系统级审批和隔离。

可概括为：

```text
目标与事实来源 → Agent 读取规则 → 现有平台调用工具 → 项目检查器验证结果
                                      ↓
                        附证据、按风险交给人、更新原则
```

在这个链路中，资料库负责“应该怎样做”的设计；模型、连接器、运行环境、凭据、测试、权限和审批由外部系统提供。因此，不同 Agent 平台对同一份规则的遵循效果可能不同。真实项目需要用检查器和权限配置落实关键约束。

### 其研究对象 Grok Bot 的产品层

[`reference/PRODUCT.md`](https://github.com/unicodef1wn/grokbot-field-notes/blob/02780c04ef5f412b28573bce6f82afd15d195d1f/reference/PRODUCT.md) 记录的是直播中对 Grok Bot 产品机制的描述，例如持久角色、独立记忆、计算环境、分享与权限。这是 2026 年 9 月直播的二次整理快照。它不构成本资料库已经实现这些机制的证明，也不能代替当前产品的官方文档或实测。

## 三、典型使用场景

| 场景 | 可取用的资料 | 落地需要补齐 | 合适的完成证据 |
| --- | --- | --- | --- |
| AI 辅助开发 | `AGENTS.md`、PR 模板、验证指南 | 项目运行命令、功能地图、测试环境 | 复现前后步骤、截图或实测数据 |
| 多 Agent 协作 | 编排指南、角色目录、岗位流程 | 平台消息传递、权限、事实共享和交接机制 | 清楚的负责人、输出与验收记录 |
| 支持与运营 | 客服、营销、销售等 playbook | 真实知识库、账户权限、对外发送审核 | 引用来源、草稿、审批和结果记录 |
| 研究与内容生产 | 来源、结论和证据的写法 | 自己的来源规范、链接核验和页面检查 | 固定版本引用、清晰标明推断与实测 |

### 一个工程任务示例

如果网页按钮失效，可以先让 Agent 运行真实页面并重现点击路径；随后限定修复范围；最后在相同环境重新走通路径，附上前后状态。仅修改代码、运行静态检查不足以证明真实按钮可用。这个示例来自验证原则的应用，不是原资料库随附的自动修复程序。

### 一个研究任务示例

如果要展示某个开源库的能力，先固定提交，再区分 README 宣称、源码支持、实际运行与个人推断；网页展示完成后检查手机布局和所有来源链接。这个示例结合了本仓库的维护规则和资料库的验证方法，属于本项目设计。

## 四、对当前仓库的意义与投入判断

本仓库现有规范已经要求按序编号、固定原仓库与研究版本、注明图片来源和许可、只添加经过验证的公网链接。资料库可以帮助补强下面三个执行动作：

1. **研究完成标准**：每项关键能力结论必须有固定版本来源；无法核实的内容标为假设或未验证。
2. **网页完成标准**：实际打开页面，检查资源、交互、窄屏布局与键盘操作；上线后再核实最终子路径。
3. **纠正原则**：当一个研究判断被证明错误时，更新研究记录，并把可迁移的核查方法加入工作规则；不要把单个事故写成僵硬的长期条款。

当前最合理的投入是保留一个详细研究网页与这些可迁移原则。研究仓库不需要因这个案例立即建立大规模 Agent 团队。若未来同类项目数量、协作角色或重复发布任务显著增加，再考虑更完整的岗位分工与验证工具。
