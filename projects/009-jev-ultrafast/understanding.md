# 从网页到编号，再从模型选择回到网页操作

本页汇总本次讨论，依据 [Jev Ultrafast 固定版本 1231850](https://github.com/browser-use/jev-ultrafast/tree/1231850a0bf1a0c0341fe408ef1668dbbfdfac46)。[交互网页](web/index.html#exchange)展示输入、点击、完成三条路径；[完整 SVG](web/assets/overview.svg)与[PNG](web/assets/overview.png)汇总原理和使用场景。

## 准确的能力描述

Jev Ultrafast 是一个以 DOM 状态为主要观察方式的网页智能体。它读取 Chrome 中当前可见且受支持的控件，生成编号选项，把用户目标、页面上下文和候选选择题发送给 TypeSafe Jev。Jev 返回操作选择和目标编号，库将其映射回具体动作与真实网页节点，复核后执行。需要输入文字时，才额外调用文本模型生成字段值。

Jev 本身已经是负责决策的模型。返回结果通常由程序直接路由至执行器；并不存在每一步都把 Jev 答案交给另一个大模型继续驱动的固定流程。文字模型接收目标、字段含义、页面上下文和近期操作，生成如 `{"text":"Zurich"}` 的值；它不负责直接点击网页。

## 谁在做什么

| 角色 | 责任 |
| --- | --- |
| 库的页面适配层 | 读取可见 DOM、标签和值；筛选控件、编号、维护节点引用 |
| TypeSafe Jev | 从当前候选操作和目标中作出选择，返回选择、概率和置信度等 |
| 可配置文本模型 | 仅在 TYPE_TEXT 时根据任务和字段生成要输入的文字 |
| 库的执行器 | 校验响应及当前页面，找到真实节点，通过 CDP 执行动作 |
| 具体业务的独立检查器 | 核对 URL、字段、筛选或结果；模型选择 DONE 本身不足以证明成功 |

## 编号的三个层次

`snapshot.js` 用 WeakMap 记录 DOM 节点对应的内部 ID，用 Map 保留 ID 到真实节点的映射。同一输入框可产生填写和点击两个动作。快照内的控件动作再依次获得 `e1`、`e2` 等动作 ID。

`model.py` 的 `action_space()` 按节点去重，创建给 Jev 的元素序号 `"1"`、`"2"` 等。每种操作分别列出合法目标，原生下拉选项还会附上选项序号，例如 `"2:1"`。某次快照的映射可以是：

```text
真实出发地输入框 → node 42
填写此框 → 动作 e2；点击此框 → 动作 e3
同一节点合并 → 模型元素 [2]

Jev 选择 TYPE_TEXT + "2"
程序查 targets["TYPE_TEXT"]["2"] → 动作 e2 → node 42 → 真实输入框
```

上面数字仅用于说明。元素序号和动作 ID 随当前观察重建，不是永久网页地址，不能跨轮拿旧编号操作新页面。

## 发给 Jev 的数据

库通过 HTTP POST 调用 `https://api.typesafe.ai/v1/systemone`，用 `TYPESAFE_API_KEY` 作为 Bearer 凭证。默认模型名为可配置的 `jev-latest`。主要结构包括：

- `state.page`：URL、标题、可见文字。
- `state.elements`：编号、名称、角色、值和支持的操作等。
- `state.recent_actions`：最近最多 10 次操作的相关信息。
- `questions.operation`：选择操作；目标和规则置于 instructions。
- `questions.click_target`、`type_text_target`、存在时的 `select_target`：为各操作选择兼容目标，同样带目标和规则。

“问题和答案”更精确地说是“问题和候选答案”，库没有预先给定正确答案。目标选择问题在一次请求里同时提出，Jev 返回的多个答案中，只使用所选操作对应的目标。

## Jev 返回后如何执行

程序读取 `answers.operation.choice`，例如 `TYPE_TEXT`，再取 `answers.type_text_target.choice`，例如 `"2"`。真实响应还有概率和置信度；程序检查选择是否来自候选集合、概率是否有效等。网页中的示例为便于阅读省略了这些字段，不能直接视为可提交的完整 API 数据。

| Jev 的选择 | 后续路径 |
| --- | --- |
| CLICK / SELECT | 映射到真实节点，复核页面和目标、定位及遮挡，再执行 |
| SCROLL / WAIT | 使用库预定义的滚动或等待逻辑，不需要元素编号 |
| TYPE_TEXT | 文本模型生成值，库校验 JSON 和文字，再复核并输入 |
| DONE / BLOCKED | 无需目标编号或文字生成；完成或停止推进，结果仍需业务验收 |

观察和执行构成循环。页面过期时重新观察；执行后等待有用状态再作下一次选择。模型输出不会直接变成任意选择器、坐标、Shell 命令或 JavaScript。上述代码机制能减少某些执行错误，不保证模型的语义选择总是正确。

## 范围、效果和场景

当前实现支持普通网页控件，不含桌面软件、手机 App、终端或文件管理执行器。网页读取也有边界：未覆盖 iframe、Shadow DOM、Canvas、上传、新标签页、嵌套滚动和任意键盘组件。快照中控件动作最多保留 250 条，可见正文最多 6,000 字符；默认循环不依赖截图。迁移到其他环境需要新增观察器、动作空间和执行器。

上游提供航班查询、Wikipedia 指定文章导航、本地酒店筛选的测量。航班一次录制 7.073 秒，新旧运行时三对同任务对照中位耗时约降 25%。这些不构成跨网站成功率或最低总费用的证据；计时范围和数据见 [research.md](research.md)。

内部网页后台、简单表单、多条件筛选、网页流程检查和个人助手的网页执行环节是可尝试的扩展方向，尚未在本研究中实现或验证。需要测试目标控件、登录态、权限、异常恢复及独立验收。若已有稳定 API，值得先比较直接调用；固定高频流程也应与确定性脚本对照。

## 对自己的价值与接入前提

可学习并复用环境到动作的适配、一次请求完成多个相关选择、节点映射、执行前复核，以及模型决策和业务验收的分工。具体模型内部的神经网络架构和训练流程没有在该仓库中实现，这份研究只能解释可见的客户端和执行层。

运行原库需要 Python 3.12+、Chrome、Browser Harness、TypeSafe API；输入任务另需兼容文本模型配置。原库新建的标签页共享现有 Chrome 配置，页面上下文会发给所配置的模型服务。上线自己的任务前，应测量独立成功率、完整耗时、总费用和失败类型。本研究网页仅运行本地教学模拟。
