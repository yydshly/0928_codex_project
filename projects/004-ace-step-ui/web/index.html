INSIDE ACE-STEP 1.5 / 04

文字怎样变成波形？

下面进入独立的模型仓库。codes 是离散的音乐表示；latents 是连续的音频潜变量。两者都要经过后续计算才能播放。

01 / 可选规划

LM → 语义 codes

基于 Qwen 的音乐语言模型可补充元数据，并预测约每秒 5 个音乐 codes。它为旋律和编排提供结构线索；关闭规划后，文本条件仍可直接引导 DiT。

离散序列 · 5 Hz

02 / 条件编码

文字、歌词、音色

描述经文本编码器，歌词经词嵌入与歌词编码器；参考音频先编码为潜变量，再提取音色特征。三路信息打包，供 DiT 的交叉注意力读取。

条件向量 · cross-attention

03 / 迭代生成

DiT → 音频潜变量

以噪声为初始状态，结合条件、源潜变量和掩码，预测每步更新方向。推理循环逐步生成连续的音频表示。

连续张量 · 25 Hz / 64 维

04 / 解码导出

VAE → 可听波形

1D VAE 解码器把压缩表示还原为 48 kHz 双声道音频。运行时支持重叠分块解码，降低一次解码的显存峰值，再按输出设置保存文件。

波形 · WAV / MP3 等

语义条件通路 描述 / 歌词 / 参考音色 → 编码向量 → DiT 交叉注意力

结构约束通路 LM codes 或源音频 → 结构潜变量 + 时间 mask → DiT 上下文

两路在 DiT 汇合，生成的音频潜变量再交给 VAE 解码。不同任务可省略或替换部分输入。
为什么既有语言模型，又有文本编码器？

可选 LM 是生成式规划器，会输出新的元数据和音乐 codes。文本编码器把已有描述转换成向量，供 DiT 理解输入；关闭 thinking 并不意味着完全不处理文本。

prepare_condition() 将 codes 经反量化与 detokenizer 还原为 25 Hz 提示；Cover 也能从源音频的潜变量得到这类结构线索。

prepare_condition ↗
DiT 每一步到底在算什么？

训练用 Flow Matching 学习噪声与干净音频潜变量之间的速度场。以源码的 Euler / ODE 分支为例，每步预测速度 v，再用时间差更新当前状态：

xnext = xcurrent − v × Δt

步数对应潜变量的更新次数，和歌曲秒数不是同一个量。seed 影响初始噪声；模型、参数或运行环境变化时，仅相同 seed 不足以保证完全复现。

generate_audio 更新循环 ↗
条件怎样影响每一段声音？

AceStepConditionEncoder 将描述、歌词和音色向量拼成序列。DiT 通过交叉注意力读取这些条件；自身注意力则处理声音序列内部的联系。源潜变量和 mask 作为另一组上下文输入。

这使同一模型能在不同输入约束下完成生成与编辑。提示词是模型的条件，不是逐条执行的硬规则。

条件编码器 ↗
为什么 Turbo 可以少步数生成？

模型团队通过蒸馏，将多步生成过程训练成少步模型；技术报告描述了从约 50 步到 8 步的路线。加速依赖专门训练的权重与采样安排，不能把普通模型的步数直接调低并期待同等效果。

Base、SFT、Turbo 的训练目标和 CFG 支持不同。UI 暴露某个参数，不代表所有模型都以相同方式使用它。

COVER / 结构条件

ENGINEERING & EXTENSION / 05

真正可借鉴的，
是这些实现取舍。

下面区分固定源码中的做法与本仓库提出的扩展建议。扩展尚未实施，也不是原库已解决的问题。

01 / 任务生命周期

持久化记录 ≠ 持久化执行

实现：任务表落盘，执行队列和结果 Map 留在 Node 内存中；逐个处理可限制同时提交给模型的负载。

扩展：由持久化 worker 接管领取、心跳、重试与完成落库；启动时对账未完成任务，让网页关闭或服务重启后仍可追踪。

02 / 模型适配

集中转换，集中承担变化

实现：一个函数将 UI 字段转换为位置数组，返回结果也依赖固定索引；异常会尝试 Python 后备路径。

扩展：固定兼容版本，建立接口契约与能力探测。按“模型不可用”和“生成失败”分类，避免把所有异常都当作需要重新推理。

03 / 作品溯源

歌曲和音频分开保存

实现：SQLite 记录标题、参数与 audio_url；文件存储保存音频内容。一次批量生成可以对应多个 songs 记录。
